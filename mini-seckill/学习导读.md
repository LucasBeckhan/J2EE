# 迷你秒杀系统：从一次点击读懂整个项目

这份导读对应当前实际代码：Vue 3 + Vite 前端、Spring Boot 同步下单后端、H2 内存数据库。请边读边打开对应文件中的中文注释。代码中没有自建订单线程池、Redis、MQ、登录认证、支付或超时取消。

## 1. 先建立目录地图

| 位置 | 职责 | 先关注什么 |

建议第一遍先按下面的调用链读一条成功路径；第二遍再看并发和异常分支；最后阅读样式与插图。不要先从一千行 CSS 开始理解 Java 业务。

## 2. 一次打开页面发生了什么

```text
浏览器 GET http://127.0.0.1:5173/
    -> Vite 返回 index.html
    -> main.js 创建 Vue 应用并挂载 App.vue
    -> onMounted(refresh) 触发首次数据加载
    -> getProducts() 和 getOrders('1001') 并发请求
    -> Vite 将 /api/... 转发到 http://127.0.0.1:8080/api/...
    -> Controller -> Repository -> H2
    -> Java 对象由 Jackson 序列化为 JSON
    -> ref 更新，Vue 自动重绘商品列表和订单列表
```

浏览器看到的请求地址仍属于前端 5173 端口。Vite 在服务器一侧请求后端 8080，因此开发时不需要在 Java 中放开任意跨域来源。前后端分离指源码、构建和进程独立，并不要求浏览器直接跨域访问后端。

生产部署时由 Nginx 返回 `dist/` 静态资源，并把 `/api/` 转发到 Java。`vite.config.js` 的开发代理不会自动成为生产服务器配置，具体示例在前端 `deploy/nginx.conf`。

## 3. 追踪一次成功抢购

例如用户 1001 购买商品 1：

1. 模板按钮触发 `buy(product)`。函数先检查 `busy`、库存快照、已购买集合和订单读取错误。
2. 设置 `buyingId`，禁用本页重复操作。此时还没有取得库存。
3. `createOrder` 发送 `POST /api/products/1/seckill?userId=1001`。
4. Controller 将路径 `1` 绑定到 `productId`，将参数 `1001` 绑定到 `userId`。
5. Controller 调用 Spring 注入的 Service 代理，代理开启数据库事务。
6. Service 检查用户参数、商品存在性、用户是否已购买。
7. Repository 执行带 `stock > 0` 条件的库存更新，检查返回的受影响行数。
8. 更新到一行后创建 `SeckillOrder`，调用 `saveAndFlush` 发出订单插入。
9. 方法正常返回后，事务代理尝试提交事务。提交成功，调用才算正常完成。
10. Controller 返回订单 JSON；前端保留成功订单、展示反馈，再查询库存和订单。
11. 两个读取请求结束后，前端解除忙碌状态。成功商品在当前用户下显示“已抢购”。

当前没有消息队列，接口也没有返回“排队中”。不要把网络等待误认为消息积压。

## 4. 为什么库存不能在 Java 里简单减一

下面是容易出问题的思路，并不是本项目的实现：

```text
A 读取库存 1
B 读取库存 1
A 把 1 - 1 = 0 写回，并创建订单
B 把 1 - 1 = 0 写回，并创建订单
最终库存虽然是 0，但创建了两笔订单
```

本项目使用以下逻辑对应的条件更新：

```sql
UPDATE products
SET stock = stock - 1
WHERE id = ? AND stock > 0;
```

检查与扣减由数据库在一条更新中协调。竞争最后一件时，不能让两个已提交的扣减都从同一件库存获得成功；没取得库存的请求不创建订单。数据库并发冲突也可能表现为锁超时等异常，不能认为所有失败都只会返回 0。

`ProductRepository` 中写的是 **JPQL**，它引用 Java 实体 `Product` 和属性 `stock`；Hibernate 负责翻译成数据库 SQL。`@Modifying` 声明这不是普通 SELECT，事务则由外层 Service 提供。

前端展示的 stock 只是最近查询结果，可能过时。禁用售罄按钮可以减少无效点击，但真正的库存安全发生在数据库更新中。

## 5. 为什么“先查有没有订单”还不够

同一个用户同时打开两个页面，两个请求可能都在插入之前查到“没有订单”。因此 `existsByUserIdAndProductId` 只负责提前反馈，不能承担并发防重保证。

真正的约束定义在 `SeckillOrder`：

```text
UNIQUE (user_id, product_id)
```

当库存至少两件且两个重复请求都通过预检查时，它们可能各尝试扣一件，但只有一笔订单能满足唯一约束。失败的插入抛出异常，对应事务回滚，撤销它自己的那次扣减。最终应当只保留一笔订单和一次有效扣减。

注意边界：竞争最后一件时，第二个重复请求也可能先在库存步骤失败，得到“售罄”，不一定总是“已购买”。成功订单和库存必须正确，具体失败文案不应被当作精确的并发执行历史。

当前限购按商品计算，没有活动 ID。以后引入多场活动时，需要重新设计唯一约束，而不是只改变前端提示。

## 6. 事务、flush、commit 和异常分别是什么

- **事务**：把扣库存与订单插入组织成同一数据库中的一组原子操作。
- **flush**：让 JPA 把待执行写操作同步到数据库，便于及时发现约束错误；不是最终提交。
- **commit**：提交整个事务。即使 flush 成功，提交阶段仍有可能失败。
- **rollback**：事务失败时撤销本事务的未提交写入；不是在 catch 中另加一条“库存 +1”。

`@Transactional` 默认针对运行时异常和 Error 回滚。项目业务异常均继承 `RuntimeException`，会从 Service 向外传播，事务代理先处理回滚，再到 HTTP 异常处理器。若在 Service 中吞掉异常并返回成功，会破坏这个预期。

当前 catch 将 `DataIntegrityViolationException` 统一解释为重复购买，是演示中的简化。该异常还可能来自其他完整性约束；以后修改表结构时要识别具体原因，不能把它当成数据库的专用“重复购买异常”。

## 7. 请求失败后页面如何处理

| 情况 | 当前行为 | 不能据此推断什么 |
| --- | --- | --- |
| 非正数用户 ID | 前端格式校验；Service 也有正数检查 | 客户端校验不等于后端鉴权 |
| 商品不存在 | 业务异常转换为 HTTP 404 | 不是售罄 |
| 已购买或库存不足 | HTTP 409，显示后端消息并刷新 | 不能确定所有竞争请求的执行顺序 |
| 网络断开、浏览器请求超时 | 展示结果不确定，提示查询订单 | 不能证明数据库没有提交 |
| 代理返回 HTML 错误页 | 使用 HTTP 状态兜底，避免 JSON 解析异常掩盖故障 | HTML 不能当成订单 JSON |
| 商品 GET 失败 | 保留已有快照并显示读取错误 | 不是商品列表真的为空 |
| 订单 GET 失败 | 显示错误，暂停本页抢购操作 | 不是当前用户没有订单 |

HTTP `fetch` 在收到 409 时不会自动抛异常，因此 client.js 必须检查 `response.ok`。只有网络失败或中止等情况才会直接 reject。

`AbortController` 中止的是浏览器等待，并没有分布式地撤销 Java 事务。项目因此不会自动重试下单 POST。后续若要可靠地恢复超时请求，应设计持久化请求号与明确的结果查询协议。

## 8. 前端几个变量为什么不能合并

| 状态 | 含义 | 为什么单独存在 |
| --- | --- | --- |
| `products`、`orders` | 两个 API 返回的事实快照 | 一个接口失败不应抹掉另一个接口成功的数据 |
| `userDraft`、`userId` | 输入草稿、已确认身份 | 编辑输入框时不能立刻改掉正在提交的用户 |
| `refreshing`、`buyingId` | 正在读数据、正在处理某个商品的提交 | 既要统一禁用操作，也要标出哪个商品正在提交 |
| `busy` | 前两者计算出的综合状态 | 使用 computed 避免手动同步第三份状态 |
| `loaded` | 是否完成过首次读取尝试 | 区分加载中与空列表；不代表所有请求成功 |
| `productsError`、`ordersError` | 两类读取错误 | 支持部分成功和独立反馈 |
| `notice` | 本次下单反馈 | 读取失败不能把已确认下单成功改写成失败 |
| `purchasedIds`、`visibleProducts` | 从订单/筛选条件得到的派生值 | 无需维护新的独立业务事实 |

`Promise.allSettled` 并发等待商品和订单请求，并收集各自成功或失败结果。它不会因其中一个失败就丢弃另一个结果；但也不提供数据库一致性快照，两次 GET 可以看到不同时刻的数据。

`ref` 在 JavaScript 中用 `.value`，在模板中通常自动解包。修改 ref 后 Vue 重新计算依赖并更新 DOM，不需要手工查找库存文字再修改。

## 9. 线程在哪里，为什么没看到 ThreadPoolExecutor

```text
浏览器异步网络请求
    -> Vite 代理
    -> 内嵌 Tomcat 的请求工作线程
    -> 同步执行 Controller / Service
    -> 通过连接池借 JDBC 连接访问 H2
```

当前应用没有显式创建业务线程池，也没有 MQ 消费线程。Web 容器自己管理请求执行资源；数据库连接池管理连接，**连接池不等于线程池**。`async/await`、`Promise.allSettled` 也不是在浏览器里创建 Java 线程池。

当前事务跟随同步 Service 调用执行。以后引入异步线程或消息消费者时，不能假定原线程事务会自动跨过去；那时需要重新定义事务边界、可靠投递、幂等与补偿。

## 10. 可以按这个顺序动手观察

1. 打开商品页，浏览器 Network 面板观察两个 GET 请求及返回 JSON。
2. 下单前后观察 POST 返回的订单，与 GET 商品中的剩余 stock 对照。
3. 在“我的订单”查看相同订单 ID；再次查看商品按钮应显示已抢购。
4. 切换到另一个演示 ID，确认订单分开显示，但库存是所有用户共享的。
5. 在 H2 控制台查询 `products` 与 `seckill_orders`，对照实体字段和数据库列名。
6. 阅读 `client.test.js`，理解 mock 网络测试验证的是错误转换，不是后端数据库并发。

推荐断点：Controller.seckill -> Service.createOrder -> updatedRows 判断 -> saveAndFlush。观察单个请求时可以逐步执行；用断点暂停事务会延长持锁时间，不适合同时用来衡量性能。

这版能帮助学习端到端调用、Spring 分层、JPA、事务、数据库并发控制与前端状态管理。Redis、MQ、分布式限流是后续迭代内容，不能从当前本地运行结果推导大规模生产承载能力。
